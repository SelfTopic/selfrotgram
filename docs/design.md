# Как устроена библиотека

Короткий рассказ о том, на чём всё держится. Детали и история решений: [журнал решений](decisions.md).

## Главная идея: ничего неявного

Что написано в коде, то и происходит. Нет данных, которые «волшебно» появляются в аргументах
хендлера по имени. Нет прокси-объекта `F`, который притворяется полем сообщения. Всё, что
нужно хендлеру, лежит в одном месте: `self.ctx`. Фильтры это обычные классы, которые можно
открыть и прочитать.

## Вторая идея: фильтр даёт гарантию, а тип её отражает

У сообщения `message.text` может не быть (фото, стикер). В большинстве библиотек хендлер
обязан сам проверить `if message.text is None`. Здесь проверку делает **фильтр**, а тип в
заголовке хендлера **обещает**, что она сделана:

```python
class Echo(MessageHandler[BaseContext[TextMessage]]):    # обещание: text есть
    query = HasText()                                    # проверка: text есть
    async def handle(self):
        self.ctx.message.text                            # str, а не str | None
```

`TextMessage` это тот же `Message`, у которого поле `text` объявлено без `None`. Такие типы
(`TextMessage`, `PhotoMessage`, `DataCallbackQuery`, `UserMessage`, ...) поставляет
библиотека, по одному на каждое необязательное поле.

Чтобы обещание не могло разойтись с проверкой, при **создании класса** (то есть при
импорте) библиотека сверяет заголовок с фильтром. Написали `TextMessage`, но забыли
`HasText()`? Получите `DefinitionError` сразу, а не `AttributeError` в проде через неделю.
Ни `cast`, ни `assert` в хендлерах не нужны.

Фильтры складываются: `HasPhoto() & HasCaption()` гарантирует оба поля, `A | B` только то,
что гарантируют обе ветки, `~A` ничего.

## Путь одного апдейта

```
Telegram ──▶ поллинг (getUpdates) или вебхук
                │
                ▼
          Update  ──▶  Dispatcher.feed_update  ──▶  параллельная обработка
                                                     (порядок — по желанию)
                │
                ▼
   мидлвари диспетчера (внешние, срабатывают на каждый апдейт)
                │
                ▼
   поиск хендлера по дереву роутеров:
       1. свои handlers роутера, по порядку списка
       2. дочерние роутеры, по порядку, вглубь
       для каждого хендлера: подходит ли вид (message / callback_query / ...)
                              и пропускает ли фильтр query
                │   побеждает первый подошедший
                ▼
   мидлвари роутеров на пути к хендлеру (внутренние)
                │
                ▼
   pre_handle ─▶ handle ─▶ (мидлвари: post_handle)
                │
      ошибка? ──▶ handler.on_error(exc) ──▶ (не обработал) Dispatcher.on_error(ctx, exc)
                │
      успех? ───▶ after_handle() и записанные defer(...): отдельные задачи, уже после закрытия
```

## Кирпичики

| Что | Зачем | Где смотреть |
|---|---|---|
| **Вид хендлера** | Один класс на одно поле `Update`: `MessageHandler`, `CallbackQueryHandler`, `MyChatMemberHandler`, ... (26 штук). Хендлер вызывается, только если заполнено именно его поле. | `selfrot/handlers/kinds.py` |
| **Фильтр** (`query`) | Класс с `async def check(ctx) -> bool`. Может ходить в БД. Гарантирует поля. | `selfrot/filter/` |
| **Контекст** (`ctx`) | Всё про текущий апдейт: `ctx.message`, `ctx.event`, `ctx.user`, `ctx.chat`, ярлыки `ctx.answer_message(...)`, `ctx.fsm`, а также ваши сервисы (поля в вашем подклассе). | `selfrot/context/` |
| **Роутер** | Группа хендлеров и мидлварей. Роутеры вкладываются друг в друга, дерево собирается атрибутами класса или `auto_connect`. | `selfrot/router/` |
| **Мидлварь** | `pre_handle` до, `post_handle(exc)` после. `False` из `pre_handle` не пускает дальше. Всё выполняется в одной задаче, поэтому `ContextVar` (сессия БД) виден хендлеру. | `selfrot/middleware/` |
| **Диспетчер** | Корневой роутер плюс запуск: поллинг или вебхук, параллельность, `on_startup`/`on_shutdown`, остановка по сигналу. | `selfrot/dispatcher/` |
| **Отложенное** | `self.defer(fn, delay=...)` и `after_handle()`: сделать позже, после закрытия хендлера и мидлварей, только при успехе. Одна спящая задача на вызов, лимит и остановка под присмотром диспетчера. | `selfrot/deferred.py` |
| **CLI** | `selfrot init` создаёт заготовку проекта (диспетчер, контекст, бот, роутеры), не трогая существующие файлы. | `selfrot/cli/` |
| **Bot** | Транспорт и все методы Bot API: таймауты, повтор при 429, разбор ответов в типы, `Bot.defaults`. | `selfrot/client/` |

## Слой, который не пишется руками

Типы Bot API (400 штук), методы (185), фильтры `Has*`, виды хендлеров, ярлыки контекста
(`ctx.answer_photo`, ...) и методы на объектах (`message.edit_text`, `callback.answer`)
**генерируются из официальной спецификации** скриптом `scripts/generate_types.py`. Вышла
новая версия Bot API, значит перегенерировали, и вся поверхность обновилась. Рукописная
часть небольшая: диспетчер, роутеры, фильтры-логика, FSM, клавиатуры.

## Параллельность и порядок

Каждый апдейт обрабатывается отдельной задачей, одновременно не больше `max_concurrent_updates`
(по умолчанию 100). Долгий хендлер никого не задерживает. Строгий порядок внутри чата или
пользователя включается явно (`ordering_key`), потому что порядок по умолчанию означал бы:
один медленный хендлер замораживает весь чат.

## Ошибки

Все ошибки библиотеки наследуют `SelfrotError`: ошибки Telegram (`TelegramForbidden`,
`TelegramRetryAfter`, ...), сети (`TelegramNetworkError`), неверное описание хендлера
(`DefinitionError`) и другие. Ожидаемые ошибки приложения (например, «не хватает денег»)
удобно превращать в ответ пользователю через `on_error` на хендлере или диспетчере.

## Чего в библиотеке нет, и это намеренно

База данных, постоянный планировщик задач (в памяти есть `defer`, он забывается при перезапуске), локализация, контейнер зависимостей. У приложения свои
представления об этом, а навязанный вариант превращается в неявную часть. Библиотека
даёт места, куда всё это встаёт явно: `create_context` (сервисы приложения), мидлвари
(сессия на апдейт), `on_startup`/`on_shutdown` (фоновые воркеры).
